# Weather and Luna provider contracts

Checked against the providers' official documentation on 2026-08-02.

## Question

What provider contracts should Daily use to render the agreed Weather card: current temperature, a deterministic icon for the day, daily minimum and maximum temperature, precipitation chance, maximum wind speed, and an optional one-sentence forecast generated by GPT-5.6 Luna without sending user identity or location data to OpenAI?

## Decision summary

Use one Open-Meteo Forecast API request for the user's Weather Location and local calendar day. Normalize that response into two separate inputs:

1. a required display forecast used directly by the email renderer; and
2. an identity-free summary forecast sent to `gpt-5.6-luna` through the OpenAI Responses API.

The visible icon must be selected in application code from Open-Meteo's daily `weather_code`; Luna must only produce the optional sentence. Open-Meteo failure or missing required display fields makes Weather `Temporarily unavailable`. Luna timeout, refusal, incomplete response, invalid schema, or invalid sentence must not fail Weather or the email: omit the sentence and render the factual weather values.

## Open-Meteo request contract

Call `GET https://api.open-meteo.com/v1/forecast` with:

| Parameter | Value |
| --- | --- |
| `latitude`, `longitude` | Coordinates from the configured Weather Location |
| `timezone` | The user's configured IANA time-zone name; do not use `auto` |
| `start_date`, `end_date` | The same target local date in `YYYY-MM-DD` form |
| `current` | `temperature_2m` |
| `daily` | `weather_code,temperature_2m_min,temperature_2m_max,precipitation_probability_max,wind_speed_10m_max,wind_gusts_10m_max` |
| `hourly` | `temperature_2m,precipitation_probability,precipitation,snowfall,weather_code,wind_speed_10m,wind_gusts_10m` |
| `temperature_unit` | `celsius` |
| `wind_speed_unit` | `kmh` |
| `precipitation_unit` | `mm` |
| `timeformat` | `iso8601` |

Open-Meteo requires `timezone` when daily fields are requested. With a time zone, timestamps are returned in local time and daily data starts at local midnight. It also supports an explicit `start_date`/`end_date` interval, which makes the delivery's target date explicit instead of relying on the provider's default seven-day window. [Open-Meteo Forecast API parameters](https://open-meteo.com/en/docs#api-documentation)

The selected variables map directly to the agreed display:

- `current.temperature_2m` is the large current temperature. Open-Meteo documents current conditions as model data based on 15-minute intervals; it is not a weather-station observation. [Open-Meteo current weather](https://open-meteo.com/en/docs#current-weather)
- `daily.temperature_2m_min` and `daily.temperature_2m_max` are the day's minimum and maximum at 2 metres.
- `daily.precipitation_probability_max` is the maximum precipitation probability for the day.
- `daily.wind_speed_10m_max` is the maximum wind speed at the standard 10-metre level and is the value shown as `Wind up to … km/h`.
- `daily.wind_gusts_10m_max` is retained for Luna but is not a separate visible metric.
- `daily.weather_code` is the most severe condition on that day and is the sole input to deterministic icon selection. [Open-Meteo daily variables](https://open-meteo.com/en/docs#daily-parameter-definition)

Hourly values give Luna enough timing information to distinguish morning, afternoon, and evening conditions. Open-Meteo defines hourly precipitation as the preceding-hour sum, snowfall as centimetres in the preceding hour, precipitation probability as the probability for the preceding hour, wind gusts as the preceding-hour maximum, and weather code as an instantaneous WMO code. [Open-Meteo hourly variables](https://open-meteo.com/en/docs#hourly-parameter-definition)

### Response validation

Validate provider JSON before normalization. The response is usable for the display only when:

- `current.temperature_2m` and its `current.time` are finite/present;
- the daily arrays contain exactly one entry for the requested target date;
- the required daily values are finite/non-null and the WMO code is recognized;
- all units match the requested units; and
- parallel hourly arrays have equal lengths and valid local timestamps.

Malformed hourly data should not discard otherwise valid display data. It should suppress the Luna call and therefore omit only the optional sentence. A malformed/missing current or required daily field should return Weather as `Temporarily unavailable` rather than inventing a value.

The generation path must ensure the target date is still “today” in the user's time zone. `current.temperature_2m` represents the provider's current instant, not the explicit `start_date`; using it in a delayed delivery for another date would mix two temporal contexts.

## Deterministic icon contract

Map the one daily WMO code to a local, email-safe icon asset. The daily code already represents the most severe condition for the day, so Luna must not choose or override it. Open-Meteo publishes these code groups: clear (`0`), mainly clear/partly cloudy/overcast (`1–3`), fog (`45,48`), drizzle/freezing drizzle (`51–57`), rain/freezing rain (`61–67`), snow (`71–77`), rain showers (`80–82`), snow showers (`85,86`), thunderstorm (`95`), and thunderstorm with hail (`96,99`). [Open-Meteo WMO code table](https://open-meteo.com/en/docs#weathervariables)

The exact asset mapping can use one asset per product category, for example clear, partly cloudy, cloudy, fog, rain, snow, and thunderstorm. Unknown future codes must use a neutral unknown-weather asset and must never be sent to Luna as a made-up description.

## Normalized Luna input

Construct a new object rather than forwarding the Open-Meteo response. It must contain no name, email, city label, latitude, longitude, address, or IANA time-zone identifier. Local clock labels are sufficient for time-of-day wording:

```json
{
  "units": {
    "temperature": "celsius",
    "precipitationProbability": "percent",
    "precipitation": "millimetres",
    "snowfall": "centimetres",
    "wind": "kilometres_per_hour"
  },
  "current": { "temperature": 18 },
  "day": {
    "weatherCode": 2,
    "minimumTemperature": 12,
    "maximumTemperature": 22,
    "maximumPrecipitationProbability": 35,
    "maximumWindSpeed": 24,
    "maximumWindGust": 39
  },
  "remainingHours": [
    {
      "localTime": "08:00",
      "temperature": 18,
      "precipitationProbability": 5,
      "precipitation": 0,
      "snowfall": 0,
      "weatherCode": 2,
      "windSpeed": 11,
      "windGust": 19
    }
  ]
}
```

Include the current local hour and later rows through `23:00`; do not include elapsed hours that could cause the model to describe past weather as upcoming. Daily aggregates still describe the whole local day. Preserve numeric values and WMO codes rather than pre-writing prose that could bias the summary.

This data minimization is worthwhile even though OpenAI states that API data is not used to train models unless the customer opts in. By default, API prompts and responses may still appear in abuse-monitoring logs retained for up to 30 days. The Responses endpoint supports Zero Data Retention for approved customers, subject to documented limitations. [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data#default-usage-policies-by-endpoint)

## Luna request and response contract

Use `POST /v1/responses` with model ID `gpt-5.6-luna`. OpenAI describes Luna as the cost-sensitive, high-volume GPT-5.6 tier; the model supports the Responses endpoint and Structured Outputs. The free usage tier is not supported. [GPT-5.6 Luna model](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

Recommended request characteristics:

- `model: "gpt-5.6-luna"`;
- `reasoning: { effort: "none" }` as the latency/cost baseline for this simple transformation, with `low` considered only if representative evaluations show a quality gap;
- no tools, web search, file search, conversation, or previous-response linkage;
- `store: false` to avoid intentional response storage (this does not remove default abuse-monitoring retention);
- low output-token ceiling appropriate for a tiny JSON object;
- a developer instruction that requires one factual English sentence of at most 15 whitespace-delimited words, based only on the supplied weather values, prioritizing unusual/actionable conditions and their local time of day, with no location, greeting, recommendation, or unsupported claim;
- normalized weather JSON as the user input; and
- strict Structured Output in `text.format` with this shape:

```json
{
  "type": "json_schema",
  "name": "daily_weather_summary",
  "strict": true,
  "schema": {
    "type": "object",
    "properties": {
      "summary": { "type": "string" }
    },
    "required": ["summary"],
    "additionalProperties": false
  }
}
```

OpenAI recommends the Responses API for new text-generation applications, distinguishes developer instructions (business rules) from user input (dynamic values), and warns that the raw `output` array may contain multiple item types. Use the SDK's parsed Structured Output/result rather than assuming text is at the first output element. [OpenAI text generation guide](https://developers.openai.com/api/docs/guides/text) [OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs)

OpenAI documents `none` as a supported GPT-5.6 reasoning effort and recommends keeping it as a latency baseline while testing `low` when a task benefits from reasoning. [OpenAI GPT-5.6 model guidance](https://developers.openai.com/api/docs/guides/latest-model#update-api-and-model-parameters)

Structured Output guarantees the JSON shape, not the product's sentence quality. After parsing, trim and validate `summary` locally: non-empty; one line; no more than 15 whitespace-delimited words; one sentence; and no numeric/location facts absent from the normalized input. Treat a refusal, incomplete response, timeout/network error, non-completed status, parse/schema failure, or failed local validation as `summary: absent`.

Do not retry Luna in the synchronous delivery path unless the existing delivery deadline has explicit room for a tightly bounded retry. The product decision is to send the mail without the summary when AI is unavailable, so the provider interface should return an optional outcome rather than throw into whole-email generation.

## Suggested application-facing contracts

```ts
type WeatherDisplayForecast = {
  observedAtLocal: string;
  currentTemperatureCelsius: number;
  minimumTemperatureCelsius: number;
  maximumTemperatureCelsius: number;
  maximumPrecipitationProbabilityPercent: number;
  maximumWindSpeedKmh: number;
  dailyWeatherCode: number;
};

type WeatherSummaryProvider = {
  summarize(input: NormalizedWeatherSummaryInput): Promise<
    | { outcome: 'available'; sentence: string }
    | { outcome: 'unavailable' }
  >;
};
```

Keep the full normalized hourly input internal to the summary provider boundary. The email renderer should receive only `WeatherDisplayForecast` plus `summary?: string`; it should neither know Open-Meteo's parallel-array response shape nor call OpenAI.

## Failure matrix

| Condition | Visible Weather result |
| --- | --- |
| Weather paused | `Paused`; call neither provider |
| Weather not configured | `Not configured`; call neither provider |
| Open-Meteo request/validation fails | `Temporarily unavailable`; do not call Luna |
| Display fields valid, hourly summary fields invalid | Render all factual display fields; omit summary |
| Luna fails, refuses, times out, or returns invalid output | Render all factual display fields; omit summary |
| Both providers succeed | Render factual fields, deterministic icon, and Luna sentence |

## Unresolved uncertainty

The official Luna model page currently lists only the `gpt-5.6-luna` alias and does not expose a dated, immutable snapshot ID. The contract can select Luna as agreed, but exact model behavior may change behind that alias. Prompt fixtures and evaluation cases therefore need to be part of implementation acceptance, and the model identifier should remain configuration rather than being scattered through rendering code.

The OpenAI documentation does not guarantee that a schema-valid string will satisfy a 15-word or one-sentence editorial rule. Local validation and omission fallback remain required even when strict Structured Outputs is enabled.
